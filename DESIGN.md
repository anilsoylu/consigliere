# Design notes

Why each piece is shaped the way it is. The README says what Consigliere does and how to
install it; this file says why it works that way. Read it before you change a hook — most
of what looks like an arbitrary choice here is a bug someone already hit.

## The topology

v1 ran an advisor and an executor. The advisor produced advice; the main Opus loop decided whether to take it, and `advisor-gate.mjs` covered only `Edit`, `Write` and `MultiEdit`. Bash, remote servers and architectural decisions were never gated, so an unconsulted decision reached the repository through any of them. Authority sat in the same loop as the tools, which is the arrangement the loop existed to prevent.

v2 moves the tools instead of adding advice. The root session runs the most capable model available — Fable 5.1 at medium effort, which the installer writes as `model: claude-fable-5-1` — and does nothing but understand the goal, choose the architecture, decompose the work, write each contract, resolve contradictions, integrate, review and report. Every code change runs in a subagent, by default a `fork` of the root: it inherits the context, the model and the prompt cache, so it starts without a discovery pass and without a restated contract. A cold `worker` is for work that runs beside something else or would flood the root's context. The plumbing — verifiers, git, gh — stays with the root, because delegating a command whose output the root has to read anyway costs a spawn and a round-trip for nothing.

- **`agents/worker.md`** and **`agents/tester.md`** — `model: opus`, `effort: medium`, the tools the root gave up. The worker holds `Read`, `Write`, `Edit`, `MultiEdit`, `Bash`, `Grep`, `Glob` and `Skill`; the tester holds `Read`, `Edit`, `Bash`, `Grep`, `Glob` and is told not to implement fixes, so a red test comes back as evidence rather than as a patch. Both escalate instead of deciding: an architectural choice, a breaking API change, a schema or migration change, a new dependency, a security decision, or a requirement whose two readings produce different code goes back to the root, which is the only place with the context to settle it.
- **`agents/explorer.md`**, **`agents/reader.md`** and **`agents/researcher.md`** — read-only. The explorer (`model: sonnet`) maps the repository and answers with `path:line`; the reader (`model: haiku`, `effort: low`) answers one question about named files so a large file never enters the root's context; the researcher (`model: opus`) answers what the repository cannot and cites a source with the version or date it holds for. They exist so the root can buy a fact without spending its own context on the search.
- **`agents/reviewer.md`** — `model: fable`, `effort: medium`, `Read`/`Grep`/`Glob`. Spawned fresh after implementation with the diff and no rationale. It keeps v1's verdict shape: **SHIP / FIX-FIRST / RETHINK**, `PROVISIONAL` when something it could not verify decides the call, and every finding labelled `[ADOPT]` / `[DISCUSS]` / `[STYLE]` / `[OVER-ENGINEERED]`.
- **`review-tier.mjs`** — a deterministic classifier that reads the working-tree diff — or any base you pass as `node review-tier.mjs . <ref>`, which is what committed branch work needs — and prints the review effort tier: `medium` for routine CRUD/UI/config diffs; `high` for business logic, sizeable refactors, and the broad risky vocabulary — auth, session, checkout, middleware; `xhigh` reserved for unambiguous surfaces: payment providers, crypto primitives, migration and schema files, plus a narrow scan of added lines for signals like `STRIPE_SECRET_KEY` or `jwt.sign`. Repeated false alarms at the top tier would teach you to ignore it, so the expensive floor is deliberately precise. The review runs at that tier before any deliverable is reported done. A `.review-tiers` file in a repo root adds per-project floors, matched against every changed path rather than only the ones a source extension covers — this repo ships its own, because `rules/`, `skills/` and `agents/` markdown *is* the product here and would otherwise classify as `none`. The model may escalate a tier with a stated reason, never downgrade one.

Every `effort:` above needs Claude Code 2.1.267 or newer. Before that build the key was dropped on exactly the models these agents name — Opus 4.7, Opus 4.8 and Fable 5 — so the ladder read as configured and ran flat. `settings.maxEffortLevel` caps the same ladder from the other side, and `doctor.mjs` warns below the floor.

## The hooks

- **`orchestrator-gate.mjs`** — a `PreToolUse` hook on `Edit|Write|MultiEdit` and on `Bash` that holds the root to deciding and delegating. It keys on `agent_id`, which Claude Code puts in the hook payload only when the hook fires inside a subagent: present means a subagent is calling and the hook exits, absent means the root is. That is why this cannot be a `permissions.deny` rule — deny rules apply to subagents too, so the entry that stops the root stops every worker with it. On a file tool it denies the source and config extensions and lets everything else through, including markdown, the config dir (`$CLAUDE_CONFIG_DIR` or `~/.claude`, and a project's own `.claude/`), the OS temp dir, `/tmp` and `~/Desktop`, so plans and scratch work stay open. The path and those roots are canonicalized with `realpathSync` before the prefix test: macOS spells both temp roots two ways, which a string compare will not collapse, and a symlink planted under one of them otherwise carried a write straight out of it. On `Bash` it fails closed against an allow-list: read-only programs, the read and plumbing subcommands of `git`, minus the forms that overwrite the working tree (`reset --hard|--merge|--keep`, `restore` without `--staged`, `checkout` with `--`, `-f`, `-B` or an existing path, `switch` with `-f`, `--discard-changes` or `-C`), the `gh` verbs a handoff needs, and a fixed set of test runners. An output redirect passes only into a temp dir, so a verifier can write the log the rules ask for; command substitution, input redirects and inline variable assignment stay denied outright, and the options that turn an allowed command into a writer or a launcher are named (`sort -o`, `find -exec`, `rg --pre`, `gh api -X POST`, and the rest). An expression it cannot parse is denied, because a restriction that waves through what it does not understand is not one. Self-gated on `rules/orchestrator.md`: deleting the rule turns the gate off, and the check runs before the payload is read so a disabled gate never denies. The `agent_id` field is Claude Code's and carries no stability guarantee, so the gate reads it as a non-empty string rather than for truthiness, and `doctor.mjs --probe` verifies the assumption against the installed build instead of leaving it asserted in a comment. Concretely, on `Edit`/`Write`/`MultiEdit` it denies `ts tsx js jsx mjs cjs py go rs rb php java kt swift c h cpp hpp cc vue svelte sql sh json yaml yml toml`, and on `Bash` a segment has to name one of:
  - `ls cat head tail wc file stat du df find grep rg sort uniq cut tr echo pwd which env date jq tree basename dirname realpath readlink diff`
  - `git status diff log show blame ls-files rev-parse merge-base describe` plus the plumbing `add commit push fetch pull checkout switch branch tag rebase restore reset`
  - `gh pr view|list|diff|create|edit|ready|merge|comment|checks`, `gh issue view|list`, `gh repo view`, `gh run view|list`, `gh release view|list`, and `gh api` only without a request body and only with `GET`
  - the verifiers: `node --test`, `npm|pnpm|yarn|bun test` and `run test*`, `npx vitest|jest|mocha|tap`, `pytest`, `go test`, `cargo test`, and `node ~/.claude/hooks/review-tier.mjs`

  Segments split on `;`, `&&`, `||`, `|`, `&` and newlines, with quoted spans masked so `jq '.a | .b'` stays one segment. Options that turn an allowed command into a writer or a launcher are denied by name: `sort -o`/`--output`/`--compress-program`, `tree -o`, `git --output`, `find -fls`/`-fprint`/`-fprintf`, `rg --pre`, `find -exec`/`-execdir`/`-delete`/`-ok`/`-okdir`, and `env` used to run a program rather than print the environment.
- **`read-gate.mjs`** — a `PreToolUse` hook on `Read` and `Bash` that denies the root a `Read` of a file over 350 lines (`READ_GATE_MAX_LINES`) without `limit`, and a `cat` or unbounded `head`/`tail` of one. A file the root reads is re-read on every later turn and inherited by every fork, so one large file is paid for repeatedly for the rest of the task; the deny names the file and points at `reader`, which answers the question and keeps the contents out of the caller's context. Subagents pass, and so does anything the hook cannot parse or stat: this is a cost guard, not a safety guard, and a cost guard that blocks work it misread is worse than the cost.
- **`plan-capture.mjs`** — a `PostToolUse` hook on `ExitPlanMode` that copies an approved plan beside the code it plans. Plan mode already writes to `~/.claude/plans/<slug>.md`, but that location is machine-local, is not partitioned by project, and the slug names no repo, so the plan is invisible to git, to a reviewer, and to you on another machine. The hook lands every approved plan in `plans/` at the repo root as `NNN-<slug>.md`, numbered after the highest already there, with its row appended to the status table in `plans/README.md` — created from `improve`'s template when absent. Priority, Effort and Depends on come from the plan's own Status block; the status starts at `TODO`. A repo whose `plans/` already means something else uses `advisor-plans/`, the same escape hatch `improve` takes. One numbering and one index, so `/improve` continues from where plan mode stopped: a re-plan in the same session reuses the slug but takes the next number, so it never overwrites the plan it replaces. It creates `plans/` at the moment it has a plan to write, because an earlier version that required the directory first failed the way silent opt-ins do — the plan for this feature was dropped, in this repo, with nothing said. It is the only hook here that writes into your working tree; a repo that would rather not commit captures puts `plans/` in `.gitignore`, which is what this repo does. `ExitPlanMode` carries no plan text, so the hook reads the path from the last `plan_mode` attachment in the session transcript and exits silently when there is none or the file it names is gone. A rejected plan leaves nothing behind: `PostToolUse` fires only after a tool completes, and rejecting a plan is a permission denial. Outside a git repo nothing is created and nothing is written.
- **`payload-probe.mjs`** — not installed and not registered anywhere; it stays in the repo and runs only during `doctor.mjs --probe`, which writes a settings file of its own that hangs this hook on `PreToolUse`/`Bash`, then runs `claude -p` with a prompt that makes one Bash call on the main thread and one inside a general-purpose subagent. The hook appends the payload it was handed to a log; the doctor asserts that the root record has no `agent_id` and the subagent record has one, and records the `claude --version` it proved that against. The run uses `--setting-sources ''` so your own hooks and `CLAUDE.md` stay out of it — not `--bare`, which does the same but refuses OAuth and would need an API key.
- **`update-check.mjs`** — a `SessionStart` hook that shows you one line when a newer tag exists upstream, naming `/consig-upgrade`, so an update surfaces by itself instead of you handing Claude the repo and asking. It goes to you rather than into Claude's context: you are the only one who can run the command, and a mention the model has to choose to make is one it drops mid-task. On a new session or a `/clear` only — a banner that came back after every compaction would be nagging with nothing new. At session start it reads a cached answer and exits; at most once a day it hands the network work to a detached child that runs `git ls-remote --tags origin` in the clone you installed from and writes the result for the *next* session. That `git ls-remote` is the only thing this package ever sends anywhere: one tag listing, to the remote of a repo you already cloned. Offline costs nothing, a fork checks its own origin rather than this one, and the clock advances whether or not the lookup succeeded. It stands down entirely under `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` or `CONSIGLIERE_NO_UPDATE_CHECK=1`; with either set — and this repo's own recommended env sets the first — `node doctor.mjs` makes the same comparison on demand and blocks while it does, because blocking in a CLI you ran on purpose is fine. See [Updating](README.md#updating).
- **`commit-language.mjs`** — a `PreToolUse` hook that blocks a `git commit` or `gh pr create` whose message reads as Turkish. Speak whatever you like in the session; what lands in the repository is English, and this catches the leak while the text is still free to rewrite. Backticked and quoted spans are exempt, so a body can quote user-facing product copy in its own locale. Self-gated on `rules/communication.md`, which this package does not ship, so a default install carries it inert until you write that rule yourself. A message it cannot read — `-F`, `--body-file` — passes: a block no rewrite can clear is how a hook earns being turned off, and a miss only leaves the status quo.
- **`git-discipline.mjs`** — a `PreToolUse`/`UserPromptSubmit` hook that enforces the git rules of `rules/workflow.md` at the three moments they are machine-visible: a commit aimed at `main`/`master` (branch first), a subject that is not conventional (`feat: …` and friends), and a `gh pr create` before any handoff skill — `/cpr`, `/clean`, `/pr-update`, `/pr-ready` — has run this session, whether Claude invoked the skill or you typed the slash command. Self-gated at runtime on `rules/workflow.md` (and, for the PR gate, on the `clean` skill being installed), so a default install without `--with-workflow` carries it inert. Anything it cannot parse — an interactive commit, `-F file`, a `$(…)` subject — fails open, same doctrine as `commit-language.mjs`.
- **`comment-ratio.mjs`** — a `PostToolUse` hook that counts line-leading comments in the text an edit just landed and, when comments outnumber code, injects one line pointing back at the comment budget in `rules/coding-discipline.md`. It cannot block — the nudge asks for a trim while the diff is still hot. Trailing comments, docstrings, and small edits stay uncounted so the nudge fires rarely enough to stay heard. Self-gated on `rules/coding-discipline.md`.

## The rules

- **`orchestrator.md`** — the behavioral spec Claude reads every session, and the file `orchestrator-gate.mjs` self-gates on. It names what the root owns, the seven roles and when to reach for each, the six-part contract every delegation carries, how parallel and dependent work are laid out, and what a subagent escalates instead of deciding. It stays short because it is loaded into every session: the gate enforces the boundary, and the rule only has to say what to do when the deny arrives.
- **`coding-discipline.md`** — a short rule that keeps the *worker* honest: state assumptions before coding, write the minimum that solves the problem, touch only what the request implies, and treat a comment as a last resort — default to none, and when one is genuinely needed keep it short and make it say *why* rather than restate the code. It holds the repo's own prose — README, design docs, PR bodies, commit messages — to the same plainness, so a line written for rhythm gets cut like a comment that restates its code. Independent of the topology; useful on its own.

## The skills

- **the `shadcn` skill** — shadcn/ui's own skill, carrying this repo's edits to its rules: when to reach for Base UI versus Radix, how composition and forms are supposed to look, icons, styling, chat surfaces. Model-invoked rather than a slash command, so it costs nothing until Claude is actually writing shadcn code, and then it stops Claude from inventing component APIs. Upstream is [shadcn/ui](https://github.com/shadcn-ui/ui) (MIT) — the rules are modified, everything else is theirs.
- **the `grilling` skill** — a relentless planning interview, fired automatically when a fresh prompt leaves two or more material decisions open, or by hand as `/grill-me` (upstream's user-only wrapper, shipped with it). It maps the plan as a design tree and asks in rounds: every question whose prerequisites are settled goes in the current round, numbered, each with a recommended answer; the answers push the frontier outward and unblock the next round. Facts are never your job — anything the model can look up itself, it looks up; only the decisions come to you. The session ends when the frontier is empty, and the settled tree becomes the Objective and Constraints of the delegation contract — which is the point: a contract built from settled decisions instead of guesses. It never fires unattended; ralph, cron, and background runs state their assumptions and proceed. Upstream is [mattpocock/skills](https://github.com/mattpocock/skills) (MIT), edited here to a plain-markdown question format plus the delegation handoff.
- **the `consig-upgrade` skill** — the other half of `update-check.mjs`, run as `/consig-upgrade`. It pulls the clone the state file records, reinstalls, runs the doctor, and reports the version it moved between and every warning verbatim. It carries `disable-model-invocation`, so a session can never start it: this writes into your live `~/.claude`, and the moment to do that is yours to pick. The name is namespaced on purpose — a bare `upgrade` would collide with the skill you write for your own project.
- **the `yagni` skill** — the deliberate enforcement pass for that rule, run as `/yagni`. It has one job: make the code smaller without making it do less. Interfaces with one implementation, wrappers that only forward, flags nobody sets, guards for states the types already rule out, the same fact maintained in two places — including a comment that only restates the line under it, which drifts exactly like duplicated code except nothing ever fails because of it. Every finding has to answer one question — does removing this leave fewer concepts, branches, config points, layers, or maintained facts, with no behavior lost — and anything that fails it is left to the review pass. That boundary is the whole design: a simplicity pass that also has opinions about naming and architecture is a second code review with softer criteria, and you stop reading it. It ships by default because it costs nothing until you invoke it.
- **the `wizard` skill** — run as `/wizard`, it writes a bash script that walks *you* through the steps only a human can take: interactive logins, 2FA, a third-party dashboard nobody can click for you. The model scopes the procedure by reading `.env*`, the README, and every `secrets.*` reference in `.github/workflows/*`, confirms the stage list with you, then authors the stages on top of a fixed library — stage-by-stage progress, confirmation gates, hidden entry for secrets, idempotent `.env` upserts, `gh secret`/`gh variable` writes, cross-platform URL opening. That library is byte-identical in every wizard and is never hand-edited, which is what makes the output predictable. The point is the boundary it enforces: hand over what genuinely needs your terminal, not a command dumped for pasting because the model would rather not do the work. Upstream is [mattpocock/skills](https://github.com/mattpocock/skills) (MIT), edited here by one paragraph on what may be handed to a human at all.
- **the `systematic-debugging` skill** — model-invoked on any bug, no slash command. Four phases: root cause investigation, pattern analysis, hypothesis and testing, implementation — and an iron law that no fix may be proposed before Phase 1 completes, backed by a red-flag list of the rationalizations that break it. Phase 1 isn't done until there is a command that fails now and passes when the bug is fixed. Phase 3 ranks 3-5 falsifiable hypotheses rather than one, because producing a single hypothesis anchors you on it. Debug instrumentation carries a unique grep-able tag so cleanup is complete, two failed fixes on the same error send the work back to the root to be re-decided rather than into a third attempt, and 3+ means the architecture is wrong, not the hypothesis. Upstream is [obra/superpowers](https://github.com/obra/superpowers) (MIT), edited here in those four places.
- **the `implement-review-verify` skill** — ships by default, no flag. An implement task normally costs the root four turns: spawn the worker, wait, spawn the reviewer, wait, spawn the tester, wait, then decide. Every wait re-reads the whole root context to advance one step, and the reviewer and the tester never overlap even though neither needs the other's answer. Handed to this skill, a `worker` carries the contract out, a `reviewer` and a `tester` judge the result at one barrier, and a single fix round closes the `[ADOPT]` findings and a red verifier — five agents at most. The fix round never repeats: two failed attempts on the same error mean the approach is wrong, and that is the root's call rather than the graph's. Every stage names an `agentType` instead of a model and an effort, so each one runs the role as your agent files define it and changing `worker.md`'s `effort:` line moves the skill without editing it. The reviewer has no shell, so the worker writes the diff to a patch file and the reviewer judges that plus the changed files, and nothing else from the worker's report. Reach for it when three or more independent contracts can run side by side; a single contract goes to a fork. It is not the handoff chain and it opens no PR — the review tier and `cpr` still run over the whole branch in the main loop.

## The recommended settings

The installer fills these in only where you have no value of your own. A key you already set is yours, even when it disagrees, and the uninstaller reverts none of them, because once a value is in your `settings.json` there is no way to tell a gap the installer filled from one you kept on purpose. Every value takes effect on the next `claude` start, and `settings.json` is backed up before the installer touches it. Delete one you disagree with and the next install puts it back, because an absent key reads as a gap; set it to your own value if you want it to stick. `node doctor.mjs` reports which of these have no value set.

- **`model: claude-fable-5-1`** decides whether any of this pays off. The root only decides and delegates, which is the work worth spending the strongest model on.
- **`CLAUDE_CODE_DISABLE_ADAPTIVE_THINKING`** and **`MAX_THINKING_TOKENS`** fix the thinking budget rather than inferring it, so a decision that looks routine does not get a shallower pass.
- **`CLAUDE_CODE_DISABLE_ADVISOR_TOOL`** keeps Claude Code's own built-in advisor tool out of the loop, where it would consult a second model server-side on top of the roles here. Set the key to `""` to get `/advisor` and `advisorModel` back.
- **`CLAUDE_CODE_DISABLE_1M_CONTEXT`** is off on purpose: the design keeps each subagent's input small and deliberate, and a bigger window works against that.
- **`subagentPromptCacheTtl: '1h'`** holds a subagent's prompt cache for an hour instead of the default five minutes, which a delegation waiting on a sibling routinely outlives. Re-delegating to the same agent after that pays for the prompt again.
- **`maxEffortLevel: 'xhigh'`** caps every `effort:` line here, on every provider. It sits at `xhigh` because that is the top of this package's own ladder: the agents ask for `high` or less, and `/merge-readiness` asks for `xhigh` on the stage that only returns a verdict. So it takes nothing away from any role, and `max` stays out of reach of a stray `/effort`.

Three env keys are deliberately left empty, because each overrides a per-role setting for every agent at once. `CLAUDE_CODE_EFFORT_LEVEL` overrides the `effort:` line in every agent file; the root's effort belongs to `/effort`. `CLAUDE_CODE_SUBAGENT_MODEL` and `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` override the `model:` line, which collapses Opus workers and a Fable reviewer into one model. The installer warns about the first and the doctor warns about all three. `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` was filled by earlier versions and is not any more, for the reason at the end of this file.

## The optional extras

- **`--with-workflow`** adds `workflow.md` plus the `ralph-protocol` skill it defers to: a bounded execution loop on top of the topology. Plans live in `tasks/todo.md` with a fixed shape — goal, acceptance criteria, verification commands, attempts, review — a verifier hierarchy decides what counts as proof, and long jobs run through `/ralph-loop` capped at 8 iterations with an explicit `RESULT: VERIFIED_COMPLETE` / `RESULT: BLOCKED` stop line. That proof is never read through a pipe: one verifier per call, output redirected to a file, because `tail` or `grep` on the end of a run hands back the filter's exit status instead of the verifier's and a red run reads as green. The rule stays short on purpose — entry conditions, iteration discipline, the verifier hierarchy and the stop conditions live in the skill, which Claude loads when Ralph actually comes up instead of on every session. The same flag ships the four handoff skills the rule names (`/clean`, `/pr-update`, `/cpr`, `/pr-ready`) and the optimization pair it wires into that order. `/optimize` is an exact-parity speed rewrite of a named routine — characterization test first, baseline timing, then shorter and faster with bitwise-identical behavior and before/after numbers required — and it fires unprompted when clean's diff read surfaces a compute-heavy routine, riding a read clean already does so it costs no extra pass. Unattended runs are bitwise-only: if parity can't hold the rewrite is reverted rather than shipped with a tolerance nobody approved. `/perf` covers the other direction, "why is this slow" with no known target. It is opt-in because it is opinionated and because the Ralph half needs a plugin this package doesn't ship; installed without it you get the planning and verification discipline and not the `/ralph-loop` commands, and the installer warns and continues.
- **`--with-merge-readiness`** adds `/merge-readiness`. The `reviewer` role gives you one verdict; this gives you a graph. Four lenses — security, data-migration, api-contract, perf — read the diff in parallel, then every finding is handed to a judge that didn't write it and told to refute it. Two rules hold it up. The judge is never weaker than the author: tier 1 is the same model at higher effort, tier 2 escalates the model instead and steps effort back down, so you never pay for both axes at once. And the judge doesn't see the author's reasoning: it gets the claim and the hunk and nothing else, because a judge that reads the justification anchors to it and approves. The verdict on whether the tree is sound comes from your own verifier's exit code rather than a model's opinion, and a baseline that is already red stops the run instead of reviewing a broken tree. Nothing in the graph writes code; every judging node is schema-bound to return a verdict, and fixes happen afterwards in a worker where you can see them. It costs up to 13 agents a run, so nothing routes here on its own.
- **`--with-release-permissions`** appends `Bash(git push:*)`, `Bash(git tag:*)`, `Bash(gh pr create:*)`, `Bash(gh pr ready:*)`, `Bash(gh pr edit:*)`, `Bash(gh pr merge:*)`, `Bash(gh pr reopen:*)` and `Bash(gh release create:*)` to `permissions.allow`, keeping every entry already there. Without the flag the installer writes no `permissions` block at all, because an allow entry is a mandatory exception that overrides matching soft denies and that is your call to make, not this package's. What it buys is an unattended release that finishes: a classifier denial mid-run leaves a branch pushed and a tag not. What it does not buy is a free hand with git — `git-discipline.mjs` still blocks bare `--force` and commits straight to master underneath it, in every thread, because a hook reads the command rather than asking a model about it. The uninstaller leaves these entries alone once written, so they are the one thing you remove by hand.

## The installer, the doctor and the uninstaller

The doctor byte-compares the installed agents and hooks against this repo's copies, because an existing but edited hook is not the hook you think is running. A missing agent file is called out specifically: the gate denies the root's source edits and names those roles as the way through, so an install without them is a lock with no key. A file you customized is reported rather than flagged.

`pins` in `.consigliere-state.json` is how a deliberate divergence survives an upgrade. `install.mjs` skips a pinned path and prints a line saying it kept yours. `doctor.mjs` counts it as a pass rather than drift, and says so in two places — the check it belongs to names it as an exception, and a `pinned files` line lists every pin — because a pinned file is left out of the comparison, and a pass that still claimed everything matched would be false about the one file you deliberately replaced. `uninstall.mjs` ignores `pins` and removes everything it installed, since an uninstall that left files behind is not one.

The uninstaller deletes a file it placed only while that file is still byte-identical to this repo's copy, for agents, hooks, rules and skills alike. Edit one and it keeps your version and tells you; the hook stays on disk but is no longer wired up. It strips only its own hook entries from `settings.json`, so an unrelated hook sharing the same block survives.

Upgrading from v1 is the same `node install.mjs`. It removes what v1 shipped and this version does not — `hooks/advisor-inject.mjs`, `hooks/advisor-gate.mjs`, `hooks/advisor-mark.mjs`, `agents/advisor.md`, `rules/advisor-executor.md` — backing each one up first, because this version ships no copy to byte-compare against and "did you edit it?" is a question that can no longer be answered. The matching hook entries are pruned from `settings.json` in the same run. Two things carry over: an `advisor-plans/` directory keeps working, since `plan-capture.mjs` still prefers it over `plans/` when it is there, and `~/.claude/hooks/advisor-watchdog.sh` — left over from the era before v1 — is in no manifest, so neither the installer nor the uninstaller touches it; the installer says so if it finds one, and you `rm` it when you want it gone.

## What context-mode cost, and why it is gone

v1 documented [context-mode](https://github.com/mksglu/context-mode) as an optional plugin and tuned two of its env keys. It is not integrated here any more. Its runtime instruction tells the model to work through Bash — `cat`, `sed`, heredocs — instead of `Read`, `Edit` and `Write`, which routes every file write around the `Edit|Write|MultiEdit` tools. `comment-ratio.mjs` never sees the text, and neither does the file half of `orchestrator-gate.mjs`. Its saving is real; it is not worth paying for by disabling the hooks that hold the topology up.

## Three choices that hold it together

- **The boundary is a hook keyed on `agent_id`, not an instruction.** A rule that says "delegate" is advice the model can talk itself out of, which is exactly how v1 failed. Claude Code sets `agent_id` in the hook payload only inside a subagent, so its absence is a reliable signal that the root itself is calling — and the one thing `permissions.deny` cannot express, since deny rules apply to subagents too and would block the workers along with the root. The root is left with markdown, plans, notes, the config dir, `/tmp` and the plumbing commands, which is enough to plan and hand off with and not enough to implement with. The field is upstream's, though, so the assumption is checked rather than trusted: `doctor.mjs --probe` reads it off a real root call and a real subagent call on the build in front of you, and a newer Claude Code makes the recorded verdict stale enough to say so at session start.
- **The Bash allow-list fails closed.** Anything the gate cannot parse is denied, and a command has to name an allowed program to pass rather than avoid a forbidden one. Command substitution, input redirects and inline variable assignment go first, because each one hides the real command from every check after it; an output redirect survives only when its target is a temp dir; then options like `sort -o`, `find -exec` and `rg --pre` that turn a reader into a writer. A blocklist would have to enumerate every way to write a file, and the first one missed is silent.
- **The reviewer is the strongest model on the freshest context.** Before source work is reported done, `review-tier.mjs` picks the effort tier from the diff; `high` and `xhigh` spawn one `reviewer` with the tier named in its prompt, and `medium` is covered by the verifier and the root's own diff read. One review per PR: an `[ADOPT]` finding is closed by a fork's fix and a green verifier, never by a second review; a diff reviewed inside `implement-review-verify` is not reviewed again at the handoff; `merge-readiness` runs only when you ask for it. The handoff ends in `cpr`, clean then pr-update in one pass. The reviewer is Fable, not Opus, because a verdict is where capability pays for itself. It is spawned fresh with the diff and no rationale, because a judge that reads the justification anchors to it. It reports everything it finds, with no severity filtering; the root prioritizes with the user. A performance finding earns `[ADOPT]` only when its cost is readable as a complexity class — a query inside a loop, an unbounded query feeding a render; anything that needs a number to be true is `[DISCUSS]` at most, because a reviewer with no `Bash` cannot measure it. Those belong to `/perf` or to `merge-readiness`'s perf lens. Claude's own `/review` is not in this path: its frontmatter carries `disable-model-invocation`, so it only runs when *you* type it — no use to a session working while you're asleep.

Agent teams is the one Claude Code feature that would undo the third. With `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` a named spawn becomes a teammate, and a teammate's agent file is appended to the default system prompt instead of replacing it, with effort inherited from the lead. The reviewer would then judge the diff at the root's effort with the default prompt underneath it, which is neither the fresh context the design turns on nor the tier `review-tier.mjs` picked. v2.0 recommended the flag; this version no longer sets it, and the doctor warns while an older install still carries it.
